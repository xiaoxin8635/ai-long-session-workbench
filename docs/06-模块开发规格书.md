## 2. M-00 公共约定（所有模块遵守）

### 2.1 配置体系

- `pydantic-settings`，环境变量前缀 `MEMORY_SERVICE_`，本地读 `deploy/.env` 之外的 `services/memory-service/.env`（git 忽略）
- 配置集中在 `app/core/config.py` 的 `Settings` 类，禁止散落 `os.getenv`

### 2.2 统一错误结构（RFC 7807）

```json
{ "type": "https://echodesk.errors/permission_denied",
  "title": "Permission denied", "status": 403,
  "detail": "workspace 不存在或无访问权限", "trace_id": "uuid" }
```

全局 exception handler 统一包装；业务异常继承 `AppError(code, http_status, detail)`。

### 2.3 trace_id 透传

- 入口中间件生成/读取 `X-Request-ID`，存 `contextvars.ContextVar("trace_id")`
- Langfuse span、日志、响应头、`messages.metadata.trace_id` 全部使用同一值

### 2.4 Schema 命名

`XxxCreate` / `XxxUpdate` / `XxxRead`（响应）/ `XxxReadBrief`（列表项）。响应模型一律含 `id` 与 `created_at`。

### 2.5 数据访问纪律

- 只有 `app/repositories/` 层访问 DB；repository 方法必须接受 `workspace_id` 并写入 WHERE（隔离第一道防线）
- 服务层校验成员资格（第二道）；向量库按 workspace partition（第三道）

### 核心接口（实际实现）

```python
# ---- 写路径 ----
async def extract_pipeline(*, ws_id: UUID, user_id: UUID, session_id: UUID,
                           messages: Sequence[tuple[UUID, str, str]]) -> list[Memory]:
    """生产组装入口（自管理 db session，后台任务调用）：
    embedding 未配置立即返回 []；全程异常内部吞掉，绝不阻塞主对话。"""

class MemoryExtractor:
    async def extract(self, messages: list[tuple[UUID, str, str]],
                      *, window: int = 20,
                      known_keys: Sequence[str] = ()) -> list[ExtractedFact]:
        """json_mode 请求，transcript 带 [message_id] 标注支撑溯源；
        known_keys 非空时注入复用规则（同主题必须复用已有 key，仅新主题新建）；
        Raises LLMError/ExtractionError —— 调用方降级为跳过本轮。"""

class MemoryDeduplicator:
    async def find_duplicate(self, db, *, ws_id: UUID, key: str,
                             embedding: list[float] | None) -> Duplicate | None:
        """三层路径：key 精确命中（similarity=1.0，strict）→ 向量 ≥0.92 判重（strict）
        → 0.80 ≤ sim < 0.92 疑似冲突层（strict=False，仅仲裁定位矛盾、禁 MERGE）；
        无向量时仅走 key 路径。"""

class ConflictResolver:
    async def resolve(self, old: Memory, new: ExtractedFact) -> ConflictOutcome:
        """LLM 仲裁：MERGE（合并正文/confidence、version+1）/
        SUPERSEDE（新条挂 supersedes_id 版本链，旧条置 superseded）/
        COEXIST（双条置 conflicted 待用户裁决）；
        失败/解析非法降级 COEXIST（保守不丢信息）。"""

# ---- 读路径 ----
class MemoryRetriever:
    async def retrieve(self, db, *, ws_id: UUID, user_id: UUID, query: str,
                       top_k: int | None = None) -> list[ScoredMemory]:
        """query 向量化 → pgvector HNSW 余弦召回 candidate_k=20
        （active/未过期/semantic+episodic+procedural/归属过滤）
        → 重排(sim*0.6 + importance*0.2 + recency*0.15·30 天半衰期 + hit*0.05·饱和 20；
          三期权重：hit 累积量降权钳制马太——20 次饱和满分曾让高频条目以
          0.15 分差恒压高 sim 冷条目，fix_v10_mh 100 行全量 recall 崩至 0.22)
        → 同 key 保留最高分 → top_k=8 → hit_count+1 + HIT 事件。"""
```

### 抽取 JSON Schema（LLM 输出约束）

```json
{ "facts": [
  { "key": "job.字节.进度", "content": "三面通过，等 HR 面",
    "memory_type": "semantic", "confidence": 0.88, "ttl_days": 30,
    "importance": 0.7, "source_message_ids": ["..."] } ] }
```

> memory_type 合法值 semantic/procedural（episodic 由 M-06 滚动摘要管线负责）；
> confidence < 0.5 的条目在管线层丢弃（控噪）。

### 关键测试（10 用例，全部通过）

1. 注入"我熟悉 LangGraph"→ 检索命中该条（hit_count 与 HIT/CREATED 事件断言）

3. 仲裁无法判定 → 双条 conflicted

### 评测优化轮（2026-09-19，M-13 评测暴露问题的写路径修复）

M-13 评测实测：冲突并存率 0.625（矛盾事实因 key 漂移 + 相似度不足 0.92 绕过仲裁直接
并存）；并发 extract 出现 PG 死锁。三项修复（Fix A/B/D）：

- **Fix B — key 复用注入（治本）**：抽取前查询 ws 内 active 记忆的 distinct key
  （`memory_repo.list_active_keys`，上限 64、按最近更新截断），经 `{extra}` 规则槽
  注入抽取 prompt——同主题事实必须复用已有 key（换手机号仍写 contact.phone），
  仅新主题新建。key 稳定后精确判重命中 → 仲裁链路生效，变体 key 噪声同步收敛。
- **Fix A — 疑似冲突召回分层**：`dedup_similarity_threshold`(0.92) 保留为判重阈值
  （可 MERGE）；新增 `conflict_similarity_threshold`(0.80) 疑似冲突层——
  0.80 ≤ sim < 0.92 的同主题条目召回送 LLM 仲裁，但 `Duplicate.strict=False`
  时仲裁 MERGE 结论降级 COEXIST（防同主题不同侧面被误合并），supersede/coexist 正常生效。
- **Fix D — 死锁消除**：①候选逐条独立提交（原单事务贯穿全部 upsert，锁持有窗口
  缩至单条毫秒级，消除与并发 record_hits 的交叉持锁；同轮后续候选判重可见先前写入）；
  ②PG 死锁（SQLSTATE 40P01，驱动异常经 SQLAlchemy 包装为 DBAPIError、orig 携带
  sqlstate）回滚后重试 2 次带退避（0.1s/0.2s——实机曾现二次死锁，重试一次不够）；
  ③生产入口 `extract_pipeline` 按 (ws_id, user_id) 进程内
  asyncio.Lock 串行化，同用户并发轮次不再同时持多行锁互相等待。
- **Fix E — record_hits 死锁防御（Fix D 之后仍漏的写路径，蟑螂法则）**：Fix 轮实机
  取证发现 chat 检索后的命中写回 `record_hits`（`UPDATE ... WHERE id IN (...)` 批量
  形态，行锁顺序由 planner 决定）与抽取管线交叉仍成三环死锁——且异常沿图冒泡被
  统一标成 `llm_upstream_error` 502，把整个对话请求炸掉（评测轮 9/20 行 chat 502
  皆此因，曾被误判为 LLM 上游抖动）。三层加固：①record_hits 改按 UUID 序逐行
  UPDATE（锁序全序化，死锁圈无法闭合）；②retriever.retrieve 内命中写回**立即
  commit**（原"commit 由调用方统一"使行锁贯穿整个 LLM 生成期，窗口缩至毫秒级，
  `expire_on_commit=False` 保证 commit 不影响后续属性读取）；③DBAPIError 降级为
  告警——命中统计是增强项，绝不阻断检索与对话。配套把图 error 事件加上 `kind`
  字段，消费方按异常类型分流 502/500（错误分类不再混淆）。

新增用例 6（known_keys prompt 注入 / 疑似冲突层 supersede / 疑似冲突层 MERGE 降级 /
死锁重试 / 命中写回死锁降级 / record_hits 乱序持久化），test_memory_pipeline.py 共 16 用例。

### 评测优化轮二期（2026-09-20，fix_v5_lt long_turn 0/2 与 Fix A 副作用的闭环）

fix_v5_lt 实测 long_turn 断言 0/2（lt-01 注入 5 条但模型不遵守节奏偏好；lt-02 时间
约束未抽成条目），另发现 Fix A 的副作用：疑似冲突降级 COEXIST 后双条 CONFLICTED
在用户裁决期间被检索完全排除，信息从上下文**静默消失**。三项修复：

- **Fix F — CONFLICTED 条目降权参与检索**：`memory_repo.search_candidates` 的
  status 过滤由仅 ACTIVE 放开为 `[ACTIVE, CONFLICTED]`；`MemoryRetriever` 重排时对
  CONFLICTED 条目乘惩罚系数 `conflicted_retrieval_penalty`(0.6，Settings 可调)——
  待裁决条目可召回但不与 ACTIVE 抢排名，预算紧张时优先被裁掉。
- **Fix G — procedural 区块行为引导语**：`ContextBuilder._render_tagged` 支持
  `_WRAPPER_HINTS`——`<procedural_memories>` 包裹标签内首行注入"持久偏好与约定
  必须逐条遵守"指令（长对话末轮 probe 时偏好注入了但模型未遵守的生成遵循缺口）。
- **Fix H — 时间/日程抽取覆盖**：`EXTRACT_SYSTEM` 判断标准显式补充"时间与日程安排

  无等待口径下 Recall/Conflict 均混入队列延迟噪声，基线轮（0.37/0.625）同样受此
  污染，A/B 对比须以等待口径重跑为准
- **两阶段回放（v2 等待口径迭代）**：逐行等待 120s 仍追不上队列尾部积压
  （memory_hit 20 行 ≈140 轮 chat，串行抽取尾部延迟可达 20 分钟，实测 9 个
  keyword 超时、全部被误判 FAIL）→ 改为三段式：并发回放全部场景（不等待）→
  批量轮询等待全部事实可见（`_wait_keywords_visible`，并发 8/间隔 5s/
  `--wait-timeout` 默认 1200s）→ 统一采集 probe。等待期间无新 chat 负载，
  队列持续消化，收敛时间可控；超时未可见的照常 probe 并在报告逐行明细中
  以 `wait_s=-1` 标注（区分"缺库噪声"与"检索失败"）
- **conflict_rate 口径修正**：并存判定限定为**两条独立条目**（条目 A 含 old_kw
  不含 new_kw + 条目 B 含 new_kw 不含 old_kw）。单条目内新旧同现不算——
  supersede 后新条目以背景口吻提及旧值（"旧号 138 已注销"）是消解的正确产物；
  旧口径实测把 6 行 probe 中 4 行误判并存（rate 0.667），库内实况 8 组冲突全部
  supersede 成功、零 CONFLICTED——纯口径误伤。报告新增逐行明细（id/wait_s/判定）
  入库，排查不再依赖手工查库
- **`--suite` 为单值参数**（非 append）：重复传参后者覆盖前者，多套件用 `--suite all`
  或分次运行
- 死锁重试增强为 2 次带退避（0.1s/0.2s）：实机验证首轮重试全部成功恢复，唯一一例
  二次死锁（与 record_hits 交叉）由增强覆盖

**fix_v4 全量串联轮追加（2026-09-20，Fix E 验证 + 容量口径发现）**：

- **Fix E 验证通过**：全量 4 套件串联 34 行（≈250+ 轮 chat）实测**错误样本 0**
  （fix_v3 同量级下曾有 9/20 行死锁 502），业务日志零 ERROR/WARNING、
  `record_hits_degraded` 降级未触发——死锁彻底消除；Fact Conflict Rate 0.0
  （vs 基线 0.625，新口径 + Fix A/B 生效）、Precision 0.989、Context Precision
  0.938 均为历史最佳
- **全量串联的队列积压伪影**：`--suite all` 单账号串联时抽取串行队列深度超过
  1200s 等待窗口（15/34 行 keyword 超时，Recall@5 被拉低至 0.35）。库内按分钟
  取证 `memories.created_at`：**评测报告生成后队列仍在消化，尾部约 7 分钟消化
  完毕，358 条记忆零丢失**——是延迟不是丢失。消化速率 ≈2~5 条/分钟（单条耗时
  以 LLM 抽取调用为主，long_turn 超长轮次显著拉长单任务耗时）
- **口径约定**：依赖异步落库的套件（memory_hit/conflict）A/B 读数以**独立账号
  分套件跑**为准（fix_v3 / fix_v3_mh：recall 0.636 / conflict 0.2）；`--suite all`
  适合 long_turn/task_continuity 或作容量压测观测
- **long_turn 逐行明细入库**：断言行补 `missed`（未命中关键词组）/`injected`
  （注入条数）/answer 截断，断言失败可区分"上下文未注入"与"注入了但没答"
